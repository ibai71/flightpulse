# FlightPulse

FlightPulse is a local aviation data engineering platform built around two independent pipelines:

```text
BTS monthly ZIPs -> Bronze Parquet -> PySpark -> Silver Parquet -> PostgreSQL staging -> dbt Gold
ADSB.aero -> local JSON -> Kafka replay -> Spark Structured Streaming -> Silver Parquet -> dbt Gold
```

The easiest Windows path is Docker Desktop plus the included PowerShell runner. It runs Python, Java, PySpark, Kafka, and PostgreSQL in containers, so a separate Ubuntu setup and local Java/Python installation are unnecessary. Downloaded data, generated Parquet, checkpoints, and credentials are kept out of Git.

## Requirements

- Docker Desktop for Windows with its WSL 2 backend enabled. The app container includes Python, Java 17, and PySpark.
- Power BI Desktop for the optional dashboard. The `.pbix` is a local artifact and is not generated by this repository.
- Network access to BTS/ADSB.aero for live ingestion. Unit tests use local fixtures and do not call external services.

## Quick start

From PowerShell in the repository:

```powershell
.\flightpulse.ps1 setup
.\flightpulse.ps1 bts
```

The first command builds the app image and starts PostgreSQL and Kafka. The second downloads the default BTS period, transforms it, loads PostgreSQL, and runs dbt. For the ADS-B demo, pass a date available in the provider's archive:

```powershell
.\flightpulse.ps1 adsb -Airport KJFK -Date 2026-04-30
.\flightpulse.ps1 test
.\flightpulse.ps1 quality
.\flightpulse.ps1 down
```

Docker Desktop must be installed and running. Its WSL 2 backend uses the Windows WSL feature, but this workflow does not require installing or configuring a separate Ubuntu distribution.

### Manual Linux/WSL execution

The commands below are still available when working directly in WSL. The Windows and Linux virtual environments are separate.

From the repository in WSL2:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
docker compose up -d postgres kafka
make bts-ingest                 # defaults to May–July 2026
make bts-build                  # Silver Parquet + PostgreSQL staging
make dbt-run                    # Build Gold models
make quality
```

For a standalone WSL setup, install Ubuntu and Docker Desktop, then install Java 17, Python 3, `python3-venv`, and `make` inside Ubuntu. Docker Desktop's WSL backend must be enabled for that distribution.

To build a different BTS period, set `START_MONTH` and `END_MONTH`, formatted `YYYY-MM`:

```bash
make bts-ingest START_MONTH=2025-01 END_MONTH=2025-03
make bts-build START_MONTH=2025-01 END_MONTH=2025-03
```

For the ADS-B demonstration, choose a date in the provider's archive. `AIRPORT` accepts an ICAO or IATA code; the default is KJFK. `ADS_B_DATE` is UTC and the default date is intentionally blank so the CLI can explain how to choose an available date.

```bash
make adsb-demo AIRPORT=KJFK ADS_B_DATE=2026-04-30
make dbt-run
```

The ADSB.aero archive date range can change. Check `https://adsb.aero/api/v1/data-range` before selecting a date. `adsb-fetch` limits the sample to a bounded number of flights, persists the raw response locally, and flattens its trajectories into replay events.

Useful commands:

```text
make help
make bts-ingest START_MONTH=YYYY-MM END_MONTH=YYYY-MM
make bts-build
make adsb-fetch AIRPORT=KJFK ADS_B_DATE=YYYY-MM-DD
make adsb-produce
make adsb-stream
make adsb-load
make adsb-demo
make dbt-run
make quality
make test
make down
```

## Data layers and outputs

```text
data/
  bronze/bts/archive/year=YYYY/month=MM/   source ZIP + manifest
  bronze/bts/parquet/year=YYYY/month=MM/   minimally parsed source rows
  bronze/adsb/                             raw API response + replay events
  silver/bts/                              typed, deduplicated flight records
  silver/adsb/observations/                streaming observations
  quarantine/                              rejected BTS rows
  quality/                                 JSON quality reports
  checkpoints/                             Spark streaming checkpoints
```

PostgreSQL receives Spark-loaded source tables in `staging`. dbt creates the analytical tables and views in `analytics`: `fact_flights`, `dim_date`, `dim_airline`, `dim_airport`, `airport_daily_performance`, `airline_daily_performance`, `route_performance`, `delay_causes`, and `fact_adsb_observations`.

The grain of `fact_flights` is one BTS-reported flight leg. The deduplication key uses flight date, DOT reporting carrier ID, reported flight number, origin/destination airport IDs, and scheduled departure time. Arrival on-time percentage is the share of eligible, non-cancelled, non-diverted flights with a valid arrival delay below 15 minutes. Cancellation and diversion rates use all scheduled flight records. Negative delays represent early arrivals/departures; null measures remain unknown.

## ADS-B replay design

The downloader first lists flights for a one-day UTC window, selects a bounded number that depart from or arrive at the requested airport, then fetches those trajectories. It stores the API response and creates one JSON event per timestamped path point. The producer sends those events to Kafka; Spark parses and validates them and writes Parquet with a persistent checkpoint. `make adsb-load` loads the resulting observations to PostgreSQL staging for dbt and Power BI. ADS-B and BTS remain separate datasets and are not joined by flight identity.

## Quality and tests

`make quality` runs pytest and `dbt test`. BTS checks report raw rows, duplicates, invalid critical identifiers, invalid airport codes, invalid distance, and status. Rows with missing critical keys or invalid airport codes are quarantined; valid records are deduplicated. ADS-B checks enforce geographic coordinate bounds. Negative delays are explicitly allowed.

The tests use `tests/fixtures/` and never call live APIs. The GitHub Actions workflow runs Python checks and dbt against a temporary PostgreSQL service. A local end-to-end run additionally requires Docker and Java.

## Power BI

Connect Power BI Desktop to the local PostgreSQL database using the connection details in `.env`. Use the `analytics` schema. Build five pages: Overview (five KPIs), Airport Performance, Airline Performance, Delay Analysis, and ADS-B Trajectories. Metric definitions are in [docs/metrics.md](docs/metrics.md); tables and source columns are documented in [docs/data_dictionary.md](docs/data_dictionary.md).

## Sources and limitations

- BTS Reporting Carrier On-Time Performance: https://www.transtats.bts.gov/TableInfo.asp?QO_fu146_anzr=b0-gvzr&gnoyr_VQ=FGJ
- ADSB.aero historical trajectory API: https://adsb.aero/api/docs
- The initial BTS default range is May–July 2026, reflecting the latest three-month period selected for the first run. Change it explicitly if BTS has published newer months.
- ADSB.aero availability and API behavior are external dependencies. The sample is bounded and stored locally; no downloaded flight data is committed.
- No Airflow, predictive ML, cloud deployment, or BTS-to-ADS-B entity matching is included in this MVP.
